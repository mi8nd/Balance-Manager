# Build Specification — Personal Balance Manager Android App

## 1. Project Architecture
- **Architecture Pattern**: MVVM (Model-View-ViewModel) + Clean Architecture principles
- **Language**: Kotlin
- **UI Toolkit**: Jetpack Compose (Material 3)
- **Navigation**: Jetpack Navigation Compose
- **State Management**: StateFlow / State in ViewModels
- **Backend**: Firebase Authentication & Cloud Firestore
- **Dependency Injection**: Manual DI
- **Data Consistency**: Atomic Firestore Transactions (`runTransaction`) for interrelated data
- **Authentication Authority**: Firebase Authentication (server-backed session validation)
- **Theme Persistence**: DataStore for Light/Dark mode preference
- **Verification Gate**: DataStore for device-local pending-email record (pre-sign-in Google takeover prevention)
- **Currency**: EGP only (Long piastres, 1 EGP = 100 piastres)

## 2. Modules
- Single module app (`app` module)

## 3. Important Directories
- `app/src/main/java/{package}/ui`: Compose UI screens and components
- `app/src/main/java/{package}/ui/theme`: Material 3 theme definition (teal/blue-green palette)
- `app/src/main/java/{package}/ui/screens`: Individual app screens
- `app/src/main/java/{package}/ui/components`: Reusable UI elements (CircularTargetProgress, ThemeToggle)
- `app/src/main/java/{package}/ui/navigation`: Navigation setup and routing
- `app/src/main/java/{package}/viewmodel`: ViewModels with business logic
- `app/src/main/java/{package}/model`: Data classes (UserConfig, Transaction)
- `app/src/main/java/{package}/domain`: Core logic (EGPFormatter, ThemeMode, ThemePreferencesDataStore)
- `app/src/main/java/{package}/data`: Repository layer (Firebase interactions, AuthenticationManager, VerificationGateStore)

## 4. UI Screens (Implemented/Planned)
- **Splash**: Loading screen during startup state determination
- **Sign Up**: Email/password registration with validation
- **Login**: Email/password authentication with validation
- **Onboarding**: Initial balance entry
- **Dashboard (Real)**: Balance, Recent Activity, Transaction actions (Income/Expense), Target configuration/tracking with circular progress, Light/Dark theme toggle
- **AI Financial Assistant**: THE single production AI destination — natural-language Q&A about the user's own transactions PLUS the integrated Transaction Intelligence insights section (Dashboard → settings gear → *AI Financial Assistant*), see §17
- **Transaction Intelligence**: PROACTIVE pattern/anomaly insight cards that live INSIDE the AI Financial Assistant screen (one destination, one app bar), see §17.3/§17.4
- **AI Smoke Test**: Debug-only connectivity check (Dashboard → settings gear → *AI Smoke Test* in debug builds only), see §17
- **Transaction History**: Full list filterable (Phase 4)

## 5. Navigation Structure
Controlled by `NavHost` in Jetpack Compose using sealed routes:
```
App Launch
  └─ SplashScreen (while determining startup state)
     ├─ Unauthenticated → SignUpScreen ↔ LoginScreen
     ├─ Authenticated (email unverified) → OnboardingScreen (Verify Email gate)
     ├─ Authenticated (no onboarding, verified) → OnboardingScreen (balance setup)
     └─ Authenticated (onboarding complete, verified) → DashboardScreen
├─ AI Financial Assistant (production, always available) — includes the Transaction Intelligence insights section
     └─ AI Smoke Test (debug builds only, `BuildConfig.DEBUG`)
```
Note: if the authenticated user's `emailVerified == false`, `StartupViewModel` routes to `OnboardingNeeded` so the verify-email gate screen appears first.

## 6. Data Models
- **UserConfig**: Stored at `users/{userId}` in Firestore
  - Fields: userId, onboardingCompleted, currentBalance, targetName, targetAmount, targetEnabled, targetCompleted, targetAcknowledged, createdAt
- **Transaction**: Stored at `users/{userId}/transactions/{transactionId}`
  - Fields: id, type (INCOME/EXPENSE), amount, description, category, timestamp
- **Monetary Representation**: Integer Long minor units (piastres, 1 EGP = 100 piastres)
- **Currency**: EGP Only (no USD, EUR, GBP, or currency selector)

## 7. Firebase Integration
### Authentication
- Firebase Auth with Email/Password + Google
- **Email/Password accounts require email verification before Google authentication is allowed** — prevents Google's trusted-provider precedence from silently replacing the password provider
- `sendEmailVerification()` is called immediately after `createUserWithEmailAndPassword` succeeds
- Session validation via `currentUser.reload()` to detect externally deleted accounts and `emailVerified` state
- Distinguishes between account deletion and temporary network errors
- AuthStateListener for real-time auth state changes (logout, user switch)

### Firestore
- Collection structure: `users/{uid}` with subcollection `users/{uid}/transactions/{transactionId}`
- Atomic Data Synchronization: Operations that mutate balance (and impact target status) use `firestore.runTransaction` to mutate `users/{uid}` and transactions atomically
- Region: me-central2 (Dammam) / Plan: Spark
- User data scoped to authenticated UID at query time (never cached across sessions)

### Security Model
- **Firebase Auth is the authoritative source of authentication and session validity**
- Firestore data is only accessible if Firebase Auth user is valid
- External account deletion is detected at startup via session revalidation
- Cached Firestore data (offline support) does NOT determine authentication state
- User-specific state (balance, transactions, target) is cleared immediately when auth becomes invalid

### Firebase AI Logic & App Check (see §17)
- App Check is auto-enforced by Firebase for AI Logic requests; installed at app start in `BalanceApplication`
- **reCAPTCHA Enterprise** is the SOLE App Check provider for BOTH debug and release builds (no Debug provider, no Play Integrity — see §18)
- AI calls use the Gemini Developer API (Gemini Developer API, no-cost on Spark) — no Gemini API key exists anywhere in the app or repo

## 8. Authentication & Session Management Architecture

### StartupViewModel
- Calls `authRepo.validateSession()` on app startup
- Reloads Firebase Auth user from server to detect external account deletions
- Routes based on session validity (not Firestore document existence)
- Handles network errors gracefully (uses cached user if available, but doesn't trust it alone)

### DashboardViewModel
- Sets up `AuthStateListener` to detect logout/session changes
- Clears all user state (balance, transactions, target, UI state) when auth becomes invalid
- Routes to authentication immediately upon auth state change
- Removes listener in `onCleared()` for proper cleanup

### FirebaseAuthRepository
- `validateSession()`: Reloads user from Firebase server; returns `Valid`, `InvalidAccount`, or `NetworkError`
- `FirebaseAuthInvalidUserException` triggers immediate sign-out and returns `InvalidAccount`
- Network errors return `NetworkError` (not treated as account deletion)
- `addAuthStateListener()`: Provides real-time auth state updates
- **Email Verification**: `signUp()` sends `sendEmailVerification()` immediately after account creation; `isCurrentUserEmailVerified()` (suspend) checks via `reload()`; `sendVerificationEmail()` resends; `syncVerificationGateState()` reconciles the server-side `emailVerified` with the device-local `VerificationGateStore`
- **Verified-Email Gate** (pre-sign-in): `authenticateWithGoogle()` consults `VerificationGateStore.isPendingVerification(email)` before any Google credential operation. If the Google email is known on this device as an unverified Email/Password account, returns `AuthResult.VerificationRequired` and performs NO Firebase mutation. This is the ONLY defense against Google's trusted-provider precedence for unauthenticated flows.
- **Verified-Email Gate** (link): `linkGoogleAccount()` checks `isEmailVerified` before calling `linkWithCredential`; returns `VerificationRequired` if unverified
- **Google Account Linking** (`linkGoogleAccount(idToken)`): Uses `FirebaseAuth.currentUser.linkWithCredential()` — the ONLY place `linkWithCredential` is called; never used for sign-in. Gated on `emailVerified`. Handles `credential-already-in-use` / `provider-already-linked` explicitly and never signs into another account
- **Google Sign-In/Sign-Up** (`authenticateWithGoogle(idToken, flowType)`): Flow-aware (never `linkWithCredential`). Pre-checks `VerificationGateStore` before any credential operation. **LOGIN** pre-checks the local explicit-link record (see `ExplicitGoogleLinkStore` below): if this device knows the Google email is a password account (via `PasswordAccountStore.getUidForEmail`) whose UID is NOT locally recorded as explicitly linked, Google LOGIN is refused immediately (`GOOGLE_NOT_LINKED`) BEFORE `signInWithCredential` — so a normal Google LOGIN can never implicitly attach `google.com` to an Email/Password account. Locally-linked password accounts and Google-only accounts (not in this device's password store) proceed to `signInWithCredential()`: authenticates an existing Google-linked account; custom-domain collision → `ACCOUNT_EXISTS_WITH_DIFFERENT_CREDENTIAL` → user signed out + `EmailCollision` returned; Login `isNewUser` branch is non-destructive (sign out + `NO_ACCOUNT`, never delete). **SIGN_UP** additionally pre-checks `PasswordAccountStore` before `signInWithCredential`: if this device knows the Google email is a password account, Sign Up refuses immediately (`ACCOUNT_EXISTS` for Google-hosted emails, `EmailCollision` otherwise) with no Firebase credential operation. The existing-account rejections therefore happen BEFORE any mutation. A defensive post-sign-in net in the SIGN_UP branch catches any account unknown to this device (same device-local limitation as the verified-email gate).
- **PasswordAccountStore**: Device-local DataStore record of emails → Firebase UIDs of Email/Password accounts known to this device (written at Email/Password sign-up AND sign-in, regardless of verification status; each email maps to the locally-known UID). Used by the Google SIGN_UP pre-check (`isKnownPasswordAccount`) and the Google LOGIN pre-check (`getUidForEmail`, to scope the explicit-link record to the exact UID rather than email-based trust). Per-device only, fail-open, same scope/limits as `VerificationGateStore`.
- **ExplicitGoogleLinkStore**: Device-local DataStore record of Firebase UIDs whose `google.com` provider was EXPLICITLY linked via Settings → Link Google Account on this device. `recordLinkedGoogle(uid)` is called in exactly one place — `linkGoogleAccount()` immediately after a successful `linkWithCredential()`. It is NEVER written when Google is merely selected in the sign-in UI, on a SIGN_UP/LOGIN attempt, or because an email matches. Google LOGIN consults it (`isGoogleLinked(uid)`, fail-closed: read error → false) and refuses `GOOGLE_NOT_LINKED` before `signInWithCredential`. Cross-device limitation (deliberate): a Google link created server-side on another device is not known locally here, so that account is refused on this device until relinked here — a documented trade-off of never implicitly attaching Google.
- **Google-authoritative domains (@gmail.com, Google Workspace)**: Google is the authoritative/verified identity provider. For an unverified Email/Password account, `signInWithCredential` silently replaces `password` with `google.com` on the same UID (proven, §10.5). The verified-email gate (above) prevents this by blocking `signInWithCredential` for unverified emails. For verified accounts, Google links as a second provider (trusted→trusted), preserving both — but ONLY through the explicit Settings link flow, never implicitly through Google LOGIN.
- **Sign-Out on failure paths**: `ACCOUNT_EXISTS` (sign-up collision) and generic exceptions during Google flows trigger an immediate `signOut()` to prevent ghost sessions from lingering
- **Email Enumeration Protection (EEP)**: `fetchSignInMethodsForEmail()` is NOT used as an authoritative pre-check; the app handles all error responses at point-of-call instead
- **Session validation on startup**: `StartupViewModel.validateSession()` calls `authRepo.validateSession()` which performs `currentUser.reload()` to detect externally deleted accounts. Additionally, `syncVerificationGateState()` routes unverified accounts to the Onboarding verify-email gate

### User Switching Safety
- Each ViewModel is fresh per navigation/Activity recreation
- No singleton user state retention
- Auth state listener ensures immediate routing on logout
- No data from previous user leaks to new user

## 9. Theme System

### ThemePreferencesDataStore
- Persists Light/Dark mode preference to DataStore (not Firestore)
- Default is Dark mode if no preference saved
- Survives app restart, recomposition, and navigation

### ThemeViewModel
- Manages `themeMode: StateFlow<ThemeMode>` (LIGHT or DARK)
- `toggleTheme()` switches between Light and Dark modes
- Reads from DataStore on init, writes on toggle

### BalanceManagerTheme
- Accepts optional `themeMode: ThemeMode` parameter
- Dynamic color is disabled (false) to ensure app palette is authoritative
- Teal/blue-green palette applied correctly in both light and dark modes

### Dashboard Theme Toggle
- `ThemeToggle` composable in TopAppBar
- Displays sun/moon emoji visual indicating current mode
- Immediately updates application theme on click
- Persists preference automatically

## 10. Money/Currency Handling (EGP Only Architecture)
- **Representation**: Strict integer representations (`Long`) denoting minor units (piastres, where 1 EGP = 100 pt)
- **Core Formatter**: `EGPFormatter` manages all Piastre ↔ UI string formatting centrally. Floating point variables entirely eliminated for calculation
- **Conversion Math Strategy**: Simple mathematical operators keeping type `Long`. Display divides by 100
- **No currency selector**: EGP is the only currency throughout the application

## 11. Target Feature

### Target Architecture
- Name, Amount (Long piastres), Enabled flag, Completed flag, Acknowledged flag
- Target progress calculated as: `(currentBalance / targetAmount).coerceIn(0f, 1f)`
- Division by zero handled safely: `targetAmount.coerceAtLeast(1L)`

### Circular Progress Ring
- Custom `CircularTargetProgress` composable
- Displays progress as circular ring (not horizontal bar)
- Shows percentage text centered in ring
- 0% = empty ring, 100% = full ring, >100% = clamped visually to 100%
- Integrates with Material 3 theme colors

### Target Completion
- When `currentBalance >= targetAmount && targetAmount > 0`:
  - `targetCompleted` set to true in atomic transaction
  - One-time celebratory modal shown
- `targetAcknowledged` persisted to prevent repeat popups
- Modal dismissed by user clears celebration flag

### 17.3 Transaction Intelligence (Task 4)
- **Markdown `---` bug — root cause & fix**: the Task 3 parser ALREADY recognized a bare `---` as `MdBlock.HorizontalRule` (existing tests passed). The reported "still broken" render had three real causes: (1) the divider used `onSurfaceVariant.copy(alpha = 0.2f)` → 20% alpha, effectively invisible so the user read "not rendered"; (2) the typewriter reveal shows `-` then `--` before `---` completes, and partial mode only hid inline markers — block-level pending dashes were emitted as literal paragraph text; (3) `HORIZONTAL_RULE = Regex("^-{3,}\\s*$")` anchored dashes at column 0, so a model reply that indented the separator (`  ---`) fell through to a literal paragraph. Fix (in `Markdown.kt`, no new dependency, no parser rewrite, no broader Markdown support): `HORIZONTAL_RULE = Regex("^\\s*-{3,}\\s*$")`; new `PENDING_HORIZONTAL_RULE = Regex("^\\s*-{1,2}\\s*$")` skipped in `partial` mode only when `paragraphLines.isEmpty()` (a `-` directly attached to paragraph text stays literal, matching the completed parse); `parseMarkdown(source, partial) = false` default keeps every existing test valid; divider color switched to `MaterialTheme.colorScheme.outlineVariant` (standard M3 divider, clearly visible). +8 regressions in `MarkdownParserTest`.

### The defect (verified on physical device 2026-09-18; evidence `e2e/evidence/qa/bug_delete_recent_auth_after_wipe.png`)
`DashboardViewModel.deleteAccount()` (see `viewmodel/DashboardViewModel.kt` `deleteAccount`) runs:

1. `userRepo.deleteUserData(uid)` — permanently purges the user's Firestore document (balance 12,740.00 EGP, goal, transactions).
2. `authRepo.deleteCurrentUser()` — Firebase Auth account deletion.

Firebase gates account deletion on a *recent-login* window. When the session predates that window, step 2 fails with `ERROR_REQUIRES_RECENT_LOGIN` — **after** step 1 has already purged all user data. Net effect (reproduced live): the account still signs in, the snackbar shows "This operation requires recent authentication. Please sign out and sign in again before deleting your account." — and the user has permanently LOST their balance, goal and transaction history.

### Live REST confirmation (both orders tried)
- `e2e/lib/qa_delete_account_recent_auth.py` is the deterministic, re-runnable oracle. It talks to Firebase REST only (works even while the device is locked), never prints secrets, never mutates. Usage: `--after` does a sign-in + Firestore user-doc GET and classifies the outcome:
  - auth alive + doc present → OK (guard held; nothing lost)
  - **auth alive + doc GONE → DATA LOSS (defect) → exit 1**
  - auth GONE + doc GONE → OK (clean full deletion)
  - auth GONE + doc present → orphaned doc (reverse defect) → exit 1
- Confirmed twice on live backend:
  - Account with an *old* session (no recent login): delete attempt failed with recent-login error, snackbar text load-exact, and REST showed `AUTH_ALIVE` + `USER_DOC_GONE` → **DATA LOSS reproduced**.
  - A freshly signed-in session (recent login): the correct full delete *does* work — auth gone (subsequent sign-in → 400 `INVALID_LOGIN_CREDENTIALS`) + token-based REST user-doc still reachable cleanly only while the hook was fresh. After an auth delete the old captured ID token still allows Firestore REST to confirm the doc is gone.

### Why this pass did NOT change auth code (blocked, leave+report)
- The device lock screen (bouncer) blocked the last renderable step, and re-verifying reordered auth code live was not possible tonight. Changing deletion ordering on a *live account* without on-device verification risks a worse outcome (e.g. orphaned Firestore doc after successful auth delete, since the fresh ID token needed to purge must be captured before deletion). Two defensible fixes exist; picking one statically without device verification is the class of change that gets committed broken.
- **Recommended fix (next pass, device available):**
  1. Require/refresh recent auth BEFORE any purge. Either (a) call `authRepo.reauthenticate(...)` with stored credentials before purging, or (b) capture the current user's ID token first, then `deleteCurrentUser()`, and purge Firestore via REST using that captured token only *after* the auth delete succeeds.
